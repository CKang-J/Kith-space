# Kith-space 愿景

> 一个人和一支有身份、有记忆的 agent 团队，共处一个属于你们的本地空间，一起把事做完。

这份文档承载 Kith-space 的理念与长远方向，是项目的北极星。它写给一个可能完全没有当前上下文的未来读者——无论是接手的人，还是需要理解项目意图的 AI。读完它，你应该能明白 Kith-space 是什么、为什么这样设计、最终要去哪里。

具体的锁定决策见 `decisions.md`，阶段划分见 `roadmap.md`，术语见 `glossary.md`，各专项设计见 `docs/kith-space/*.md`（product-brief / mvp-spec / architecture-proposal / ui-direction / migration-plan）。本文引用它们，不重复展开。

## 一句话愿景

Kith-space 是一个人和一支 agent 团队共处的协作空间，长期目标是长成一个人的工作生活操作系统。每个 agent 有自己的身份、职责和记忆，跑在你本机已有的 runtime 上（Claude Code / Codex / opencode）；你在频道里 @ 他们、或私聊派活，他们领任务、互相分派、交付结果，并通过统一的工具层操作你的任务、记忆等模块。

### 名字的寓意

Kith 是一个旧词，指“你信任的一圈熟人”——不是通讯录里的泛泛联系人，而是知根知底、能一起做事的自己人。这正是产品对 agent 的定义：不是一次性的问答机器人，而是有身份、有记忆、会持续跟你共事的团队成员。你不是每次都在跟一个陌生工具重新解释自己，而是回到一群已经了解你的人中间。

-space 有两层意思。对普通用户，它是人和 agent 真实共处、一起干活的空间；对开发者，它带着 namespace / workspace 的语感——一个有边界、可切换、装着上下文的工作区。两层合起来，就是产品想给的感觉：熟悉的一圈人，待在一个属于你们的地方。

## 核心信念

这一节讲的是理念，不是功能清单。它们是所有设计决策背后的判断标准；当未来出现取舍时，回到这几条来判断方向。

### 一、agent 是团队成员，不是一次性 bot

大多数 AI 工具把 agent 当成一个无状态的函数：给它一段提示，拿一段回答，用完即弃，下次从零开始。Kith-space 反过来假设——agent 是常驻的团队成员。

这意味着三件事必须成立：**身份**（每个 agent 有名字、头像、职责，你能一眼认出谁是谁）、**记忆**（它记得你之前说过什么、正在推进什么，不用每次重新交代）、**在场感**（它待在一个你能看见的空间里，而不是藏在某个对话框背后）。产品情感的内核，就是那种“群聊里一圈熟人一起干活”的感觉——你 @ 一个人，另一个人插一句，事情在你们之间流动。这份手感是 Kith-space 存在的理由，不能为任何效率优化让路。

### 二、harness 优先，角色通用，不做场景专用硬流程

这是 Kith-space 最重要、也最容易被误解的一条。

我们的设计重心**不在“替 agent 决定怎么做事”，而在“把 agent 做事的环境搭好”**。这个环境就是 harness：工具、上下文、记忆、协议这一整套系统条件。我们投入精力设计工具层、记忆结构、上下文供给和协作协议，让 agent 在一个信息充分、能力清晰的环境里工作。环境到位了，通用的 agent 自己就能把事做好。

由此推出两条：

**角色通用。** agent 默认是空白的，靠职责提示词获得身份，靠记忆积累经验。我们不生产“开发专用 agent”或“客服专用 agent”，只提供通用的角色框架和几个可选的起点模板——那是填空用的起点，不是产品发给你的岗位表。

**不做场景专用硬流程。** 我们不把“开发流水线”“客服工单”这类特定场景的步骤硬编码进产品。该用哪个工具、按什么顺序推进，交给 agent 依据当前目标自主决策。产品提供的是能力和环境，不是脚本。

这里要特别说清楚一件事：**开发只是众多角色场景之一。** Kith-space 绝不是“一个 AI 开发团队工具”。写代码、做调研、写文案、做测试、整理信息——这些在产品眼里是平等的，没有哪一个享受特殊的硬编码待遇。如果有一天你发现产品里出现了一条专为“做开发”而写死的流水线，那就是背离了这条信念。

这条信念的共同取舍是：**接受略低的“开箱即用完成度”，换取更高的通用性和更长的生命力。** 硬编码流程上手快，但每个新场景都要重做一遍；把环境设计好，则同一套 harness 能适配你想让 agent 做的大多数事。我们赌的是后者。

### 三、不自研 runtime，拥抱本机已有的执行内核

Kith-space 不造自己的 agent 执行内核。所有 agent 都外接你本机已经装好的 runtime——Claude Code、Codex、opencode——通过适配器接入。产品自己建设的是**模块能力**（任务、记忆，以及长远的邮箱、日历、画布等），这些能力通过 MCP 暴露给 agent 调用。

这么选有两层理由。一是务实：runtime 是一个快速演化、竞争激烈的领域，自研既跟不上，也没必要；把它交给专门做这件事的项目，我们专注做协作空间和模块层。二是理念：Kith-space 想成为一个中立的、能容纳多种 runtime 的空间，而不是绑定单一内核的封闭产品。你已经在用的工具，直接接进来就好。

代价是我们放弃了“应用内 runtime”能带来的极致顺滑上限——“原生流畅的操控”要靠一个设计良好的 MCP 层加 UI 桥接来实现，天花板略低。我们接受这个取舍。

### 四、local-first、桌面优先，一个人的工作生活 OS

Kith-space 首先服务一个人，根植于本地。工作区是一个本地文件夹，自包含、可移植——复制这个文件夹，就复制了整个工作区，包括聊天记录、agent 名册和记忆。你的数据在你自己的机器上，不经过任何强制的云端。

形态上，桌面优先（Electron 包裹 daemon + server + web），单人为主。长期目标是长成“个人的工作生活操作系统”——不只是一个干活的地方，而是你处理研究、写作、任务、信息的日常中枢。这条主线的权重高于“通用协作团队”那条辅线，产品的长期形态围绕它展开。

### 五、纯开源，宽松许可

Kith-space 是纯开源项目，采用 MIT / Apache 这类宽松许可。这不是随口一提的姿态，而是贯穿到了技术选型里：底座和参考项目都必须协议干净、可自由采用；正因为协议不兼容，AGPLv3 的 OpenLoaf 才被降级为纯设计参考，不碰其源码。

产品不走闭源商业化路线。宽松许可意味着任何人都能自由使用、修改、分发和商用，我们希望它成为一个可以被信任、被二次创造的公共基础。

## 长远愿景：MVP 只是第一个切片

这一节是本文的重点。

Kith-space 的第一版（MVP）是一个**刻意收窄的薄切片**：一个重做过外观的协作空间，加上两个摩擦最低的模块（记忆和任务）作为 MCP 工具，加上外接的本机 runtime。它要验证的核心命题只有一句——“**一个有身份、有记忆的外部 agent，在频道里通过 MCP 操作我的模块，这套手感成不成立？**”

MVP 的范围划分见 roadmap.md 和 mvp-spec.md，本文不展开“做什么”，只讲“最终要去哪里”。请把下面描绘的完整图景，理解为 Kith-space 真正的样子；MVP 是它的第一个切片，不是它的全部。

### 完整图景

**生产力模块由 agent 原生操控。** 邮箱、日历、画布这类模块会陆续进来，且都通过 MCP 暴露给 agent——agent 能读你的日程、起草并发邮件、在画布上和你共同编辑。模块不是给人单独用的附件，而是 agent 能力的延伸：你说“帮我把这周的会理一下”，它真的去动你的日历。

**模块可以提升到中间全屏工作。** 平时模块待在右侧面板里供你一瞥，但需要专注时（比如画布、日历这类“吃宽度”的模块），它能提升到屏幕中央甚至全屏，群聊让位到侧边。这是“一瞥在右栏，专注在中央”的可调驾驶舱手感。

**多真人协作。** 空间从“一个人和一群 agent”扩展到“多个真人和一群 agent”。底座里的多用户能力在 MVP 阶段休眠，长远会被唤醒——一个团队和他们共同的 agent 同事待在一个空间里。

**多设备 agent 加入 + 跨设备 / 公网访问。** agent 不再只跑在你这一台机器上，其他设备上的 runtime 也能加入同一个空间。与之配套，空间本身能被跨设备、局域网乃至公网访问（浏览器打开），并配上认证。

**写记忆的 MCP 工具。** MVP 阶段，agent 通过原生文件操作来写记忆（遵循“一事一文件 + 自动维护索引”的约定）。当自由写变得杂乱时，会提升为一个专门的 `memory_save` MCP 工具，让记忆的写入更结构化、更可控。

**bento 驾驶舱长成完整的个人 OS 门面。** 空间总览态是一个全局 bento 驾驶舱——MVP 里它很薄（空间列表 + 全局收件箱 + 简单聚合待办），长远它会长成你整个工作生活 OS 的首页：可拖拽的卡片、聚合的信息流、一眼看尽你手头所有事。这是“个人 OS”那条主线（决策中的 B 权重高于 A）最终的落点。

**成熟的人机团队协作。** 终局是这样一个流程：你对 @leader 提一个需求，leader 理解目标、把它拆解成子任务、分派给一队各有所长的 agent、跟踪进度、最后把结果汇总交付给你。你面对的是一个“团队入口”，而不是一个个孤立的对话。

### 为什么这些被放到 MVP 之后

把上面这些延后，是深思熟虑的取舍，不是能力不足或兴趣缺失。核心有两条理由。

**先验证核心手感。** 如果“有身份有记忆的外部 agent 经 MCP 操作模块”这套基本手感不成立，那么在它之上堆再多模块和协作层都是空中楼阁。MVP 用最小的面积，去押注这个最关键的问题。手感立住了，后面的扩展才有意义。

**控制复杂度，逐层解锁。** 有些能力有明确的工程坑或前置条件，硬提前只会拖垮整体质量：邮箱涉及 OAuth / IMAP 的深坑，画布对流畅度极其敏感；而跨设备 / 公网访问会直接打破“单机”这个安全前提——它必须和认证、agent 权限模型一起上线，否则就是在把一台拥有本机完全权限的机器暴露到网络上。这些不是随便就能开的开关，需要在正确的时机、配齐前置条件再解锁。

**所以请记住：这些是“延后”，不是“放弃”。** 它们在架构里被有意保留了位置——底座的多用户能力休眠而非删除，跨设备访问的入口在架构上预留、只是在 MVP 里灰掉，数据层从一开始就按“每工作区独立、可移植”来设计。愿景的完整形状，从第一天起就写进了地基。

## 非目标与反模式

明确不做什么，和明确要做什么同样重要。

- **不自研 runtime。** 永远外接本机已有的执行内核，不造自己的 agent 内核。这是硬约束，不是权宜。
- **不做场景专用硬流程。** 不把开发流水线、客服工单这类特定场景的步骤写死进产品。一旦发现产品在为某个具体场景硬编码流程，就是踩到了反模式。
- **不做闭源商业化。** 不引入协议不兼容的代码（这就是 OpenLoaf 只能做设计参考的原因），不走闭源路线。
- **不为“开箱即用完成度”牺牲通用性。** 当“硬编码一个流程能让某场景立刻好用”和“把环境设计好让通用 agent 自己搞定”冲突时，选后者。
- **不让效率优化侵蚀协作手感。** 群聊式的、agent 作为在场团队成员的手感是内核，不能为了流程自动化把它压扁成一个无声的任务队列。
- **警惕权限债。** MVP 阶段外接 runtime 拥有本机较高权限（这是已知并被记录的技术债）。一旦引入会摄入不可信内容的模块（邮箱、浏览器），权限模型必须先升级——这是提示注入通向破坏性操作的攻击链，不能拖。详见 decisions.md。

## 与四个参考项目的关系

Kith-space 不是从零起步，而是站在四个已有开源项目的肩膀上。它们现在都位于 `reference/` 目录，角色分工明确。

**open-tag（Apache-2.0）是代码底座。** 频道 / 群聊 / 私聊、任务、收件箱、多 runtime 适配器、本地 daemon 这些协作骨架直接复用；Kith-space 在其上重做外观、补齐模块、调整数据层。选它作底座而非 OpenLoaf，核心原因有二：协作空间的成熟度（open-tag 原生就有频道 / 私聊 / 任务的一等公民模型），以及协议干净（Apache-2.0，可自由采用宽松许可）。

**OpenLoaf（AGPLv3）是设计参考，仅此而已。** 它的界面质感、跨会话记忆、画布、邮箱 / 日历等模块思路都很值得借鉴，但它是 AGPLv3 的传染性协议，与本项目 MIT / Apache 的立场冲突——所以只借设计理念、用自己的代码重新实现，绝不拷贝其源码。

**openagents（Apache-2.0）和 zano（MIT）是局部参考。** 前者在多设备 workspace、共享浏览器 / 文件方面有可借鉴处；后者的频道 / 私聊交互可作轻量参照。两者都不作为底座。

---

Kith-space 的赌注很简单：把环境设计好，通用的 agent 自己就能干好活；把它们当成有身份、有记忆的自己人，人和机器就能真正地一起工作。MVP 只是这个信念的第一次落地。愿景的完整形状，已经在这里了。
