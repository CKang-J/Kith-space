# Kith-space 产品定位

本文是 Kith-space 五份设计文档中的定位文档，负责说清楚“这是什么、给谁用、为什么这样做”。架构、MVP 范围、界面方向、迁移路径分别见 architecture-proposal.md / mvp-spec.md / ui-direction.md / migration-plan.md，本文不展开这些细节。

## 一句话定位

Kith-space 是一个人和一支 agent 团队共处的协作空间：每个 agent 有自己的身份、职责和记忆，跑在你本地已有的 runtime 上（Claude Code / Codex / opencode），你在频道里 @ 他们、或私聊派活，他们领任务、互相分派、交付结果，并通过统一的工具层操作你的任务、记忆等模块。

它面向单个真人，长期目标是成为“个人的工作生活操作系统”。

### 名字的寓意

Kith 是一个旧词，指“你信任的一圈熟人”——不是泛泛的联系人，而是知根知底、能一起做事的自己人。这正是产品对 agent 的定义：不是一次性的问答工具，而是有身份、有记忆、会持续跟你共事的团队成员。

-space 有两层意思。对普通用户，它是人和 agent 真实共处、一起干活的空间；对开发者，它带着 namespace / workspace 的语感——一个有边界、可切换、装着上下文的工作区。两层合起来，就是产品想给的感觉：熟悉的一圈人，待在一个属于你们的地方。

## 目标用户与核心场景

### 主线：单个真人的个人工作生活 OS

Kith-space 首先服务一个人。你把日常要处理的事——研究、写作、任务跟踪、信息整理——交给一支常驻的 agent 团队，他们记得你之前说过什么、正在推进什么，不用每次从零交代。

这条主线的重量高于下面的辅线，产品的长期形态围绕它展开。

### 辅线：通用角色的分工协作

当一件事需要拆开做，你可以给 agent 安排角色，让他们分工。比如：

- 一个 leader 负责理解目标、拆解任务、把活派给合适的成员、最后汇总交付；
- 一个偏研究的成员负责查资料、做调研；
- 一个偏文案的成员负责起草和润色；
- 一个偏测试 / 校验的成员负责检查结果。

这些只是举例，用来说明“分工”长什么样。产品不预设这几个角色，也不把它们写死成固定流程——角色是你自己填的起点，不是产品发给你的岗位表。

## 核心理念：harness 优先

Kith-space 的设计重心不在“替 agent 决定怎么做事”，而在“把 agent 做事的环境搭好”。这个环境就是 harness：工具、上下文、记忆、协议这一整套系统条件。

具体来说，三条原则贯穿全局：

harness 优先。我们投入精力设计的是工具层、记忆结构、上下文供给和协作协议，让 agent 在一个信息充分、能力清晰的环境里工作。环境到位了，通用的 agent 自己就能把事做好。

角色通用。agent 默认是空白的，靠职责提示词获得身份，靠记忆积累经验。我们不生产“开发专用 agent”或“客服专用 agent”，只提供通用的角色框架和几个可选的起点模板（填空用的起点，不绑定流程）。

不做场景专用硬流程。我们不把“开发流水线”“客服工单”这类特定场景的步骤硬编码进产品。该用哪个工具、按什么顺序推进，交给 agent 依据当前目标自主决策。产品提供的是能力和环境，不是脚本。

这三条的共同取舍是：接受略低的“开箱即用完成度”，换取更高的通用性和更长的生命力。硬编码流程上手快，但每个新场景都要重做一遍；把环境设计好，则同一套 harness 能适配你想让 agent 做的大多数事。

## 与四个源项目的关系

Kith-space 不是从零起步，而是站在四个已有开源项目的肩膀上。它们的角色分工明确：

open-tag（Apache-2.0）是代码底座。频道 / 群聊 / 私聊、任务、收件箱、多 runtime 适配器、本地 daemon 这些协作骨架直接复用，Kith-space 在其上重做外观、补齐模块、调整数据层。

OpenLoaf（AGPLv3）是设计参考，仅此而已。它的界面质感、跨会话记忆、画布、邮箱 / 日历等模块思路很值得借鉴，但它是 AGPLv3 的传染性协议，与本项目 MIT/Apache 的立场冲突——所以只借设计、用自己的代码重新实现，绝不拷贝其源码。

openagents（Apache-2.0）和 zano（MIT）是局部参考。前者在多设备 workspace、共享浏览器 / 文件方面有可借鉴处；后者的频道 / 私聊交互可作轻量参照。两者都不作为底座。

选择 open-tag 而非 OpenLoaf 作底座，核心原因有二：协作空间的成熟度（open-tag 原生就有频道 / 私聊 / 任务的一等公民模型），以及协议干净（Apache-2.0，可自由采用宽松许可）。runtime 的取舍详见 architecture-proposal.md。

## 非目标

为了让 v1 聚焦，以下能力明确不在第一版范围内。它们不是被否定，而是被推后：

- 多真人云端协作。v1 是单真人、单机形态，多用户能力在底座里保留但休眠。
- 自研 runtime。所有 agent 都外接本地已有 runtime，产品不造自己的 agent 执行内核。
- 完整的邮箱 / 日历 / 画布模块。这些要么涉及 OAuth/IMAP 的工程坑，要么对流畅度敏感，留待模块层稳定后再做。
- 跨设备访问。v1 只支持本机浏览器访问 localhost；跨设备 / 局域网 / 公网访问会打破单机安全前提，必须和鉴权、agent 权限模型一起上线，故推后。
- 插件市场。
- 多租户 SaaS。

v1 实际交付的薄切片范围见 mvp-spec.md。

## 开源立场

Kith-space 是纯开源项目，采用 MIT / Apache 这类宽松许可。这不是随口一提的态度，而是贯穿到了技术选型里——底座、局部参考项目都必须协议干净可自由采用，AGPLv3 的 OpenLoaf 正因协议不兼容才被降级为纯设计参考。

产品不走闭源商业化路线。宽松许可意味着任何人都能自由使用、修改、分发和商用，我们希望它成为一个可以被信任、被二次创造的公共基础。
